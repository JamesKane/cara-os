# CaraOS code drift report — 2026-05-08

**Scope:** audit of `include/` and `src/` against the brand-vs-API
namespace rule documented in `docs/PRINCIPLES.md` §3.1 and
`docs/ARCHITECTURE.md` §13.

**Status:** snapshot. Do not act on these items during the current
Phase 1 sprint — the runtime contracts in `docs/PHASE1_RUNTIME.md` are
all kernel-internal and are correctly in the brand namespace as a
group. The items below are queued for the post-sprint cleanup that
seeds Phase 3 (AmigaOS source-level parity).

The audit looked for drift in two directions:

1. **Brand names squatting on API names** — kernel-internal types or
   functions taking the canonical AmigaOS spelling (`struct MsgPort`,
   `struct Task`, `AllocMem`, `AddTail`) without the canonical layout /
   signature behind it. Fixing these is required *before* Phase 3 can
   define the corresponding `<exec/*.h>` headers without a clash.
2. **API-namespace identifiers used in kernel-only contexts** — the
   inverse, where a kernel-internal helper has been given a name that
   should be reserved for the public LVO trampoline.

Items are graded **High** (ABI break or imminent name clash, address
first), **Medium** (works today but blocks Phase 3 wiring), **Low**
(cosmetic / wording).

---

## H1 — `struct MinList` does not match V36+ wire layout

**File:** `include/cara/list.h:29-32`

```c
struct MinList {
    struct ListNode head;
    struct ListNode tail;
};
```

The current implementation uses a two-pointer head + tail sentinel
layout. AmigaOS V36+ `<exec/lists.h>` defines `struct MinList` as a
three-pointer header:

```c
struct MinList {
    struct MinNode *mlh_Head;
    struct MinNode *mlh_Tail;        // always nullptr — sentinel role
    struct MinNode *mlh_TailPred;
};
```

`docs/ARCHITECTURE.md` §5.4 commits to preserving the three-pointer
layout for wire compatibility. A program that walks `mlh_TailPred`
field-by-field — common in V36+ AmigaOS code — would read garbage from
the current layout.

**Resolution (post-sprint):** convert to the AmigaOS three-pointer
layout with `mlh_*` field names; update all insert/remove primitives
to the TailPred-sentinel idiom. Internal callers that walk via
`head.succ` / `tail.pred` need an audit (currently the scheduler run
queue, signal sleeper queue, MsgPort ring of slots — see
`src/croi/sched/`, `src/croi/ipc/`).

## H2 — `struct ListNode` should be `struct MinNode` with `mln_*` fields

**File:** `include/cara/list.h:24-27`

```c
struct ListNode {
    struct ListNode *succ;
    struct ListNode *pred;
};
```

Canonical AmigaOS V36+ `<exec/nodes.h>` defines:

```c
struct MinNode {
    struct MinNode *mln_Succ;
    struct MinNode *mln_Pred;
};
```

The current name (`ListNode`) collides with no AmigaOS type but blocks
the canonical `MinNode` from existing under the same conceptual slot.
Field names lack the `mln_` prefix. Embedding sites in
`include/cara/sched.h:62` (`struct ListNode sched_node;`) propagate the
non-canonical name into every brand-namespace struct.

**Resolution (post-sprint):** rename to `struct MinNode` with
`mln_Succ` / `mln_Pred`. Add `struct Node` (full named/typed/priority
form) when Phase 3 needs it.

---

## H3 — List helper functions should be `MinList_*` (or canonical)

**File:** `include/cara/list.h:34-89`

Helpers `ListInit`, `ListAddHead`, `ListAddTail`, `ListIsEmpty`,
`ListRemove`, `ListRemHead`, `ListRemTail` cognitively occupy the
slots that V36+ `exec.library` exports as `NewList`, `AddHead`,
`AddTail`, (no `IsEmpty` — that's `IsListEmpty` macro), `Remove`,
`RemHead`, `RemTail`. The current names neither match the API
namespace (verbatim AmigaOS) nor a brand-namespace prefix.

**Resolution (post-sprint):** rename to the brand-prefixed
`MinList_AddTail` / `MinList_AddHead` / etc. per the `ARCHITECTURE.md`
§5.4 update, so kernel-internal use is unambiguous. When Phase 3
lands, the public `<exec/lists.h>` defines `AddTail` / `AddHead` /
`RemHead` / `RemTail` / `Remove` / `NewList` as exec.library LVO
trampolines that share the same underlying memory operations.

## H4 — `struct MsgPort` name squats on the public API struct

**File:** `include/cara/msgport.h:20-27`

```c
struct MsgPort {
    struct Kobj         hdr;
    struct RingHeader  *ring;
    struct RingSlot    *slots;
    u32                 capacity;
    struct Task        *owner;
    u32                 signal_bit;
};
```

V36+ `<exec/ports.h>` defines `struct MsgPort` as
`{ mp_Node, mp_Flags, mp_SigBit, mp_SigTask, mp_MsgList }`. The
current type squats on the name with a completely different layout.
A user program doing `sizeof(struct MsgPort)` or accessing
`port->mp_SigBit` would not compile against this header.

**Resolution (post-sprint):** rename kernel-internal binding to
`struct CroiMsgPort` (brand namespace) and move it under
`src/croi/ipc/msgport_impl.h` so user-facing code can never include it
by accident. Phase 3 defines the canonical `struct MsgPort` in
`<exec/ports.h>` with `mp_*` fields; the in-kernel implementation
attaches the ring / signal / owner data either as a sibling Kobj keyed
by the MsgPort pointer or as a kernel-private extension after the
visible portion.

## H5 — `struct Task` name squats on the public API struct

**File:** `include/cara/sched.h:43-63`

The current struct uses fields `name`, `pri`, `state`, `saved_regs`,
`kstack`, `sigrecvd`, `sigwait`, `sigalloc`, etc. V36+ `<exec/tasks.h>`
defines `struct Task` with the canonical `tc_Node`, `tc_Flags`,
`tc_State`, `tc_SigAlloc`, `tc_SigWait`, `tc_SigRecvd`, `tc_SigExcept`,
`tc_TrapAlloc`, `tc_TrapAble`, `tc_ExceptData`, `tc_ExceptCode`,
`tc_TrapData`, `tc_TrapCode`, `tc_SPReg`, `tc_SPLower`, `tc_SPUpper`,
`tc_Switch`, `tc_Launch`, `tc_MemEntry`, `tc_UserData`. Same name,
unrelated layout.

`ARCHITECTURE.md` §7.3 commits the public `struct Task` to V36+
fields, with kernel-private state hung off `tc_UserData` or a sibling
allocation.

**Resolution (post-sprint):** either rename the kernel-internal
binding (`struct CroiTask`, brand namespace) and re-define the public
`struct Task` in `<exec/tasks.h>` with `tc_*` fields, **or** evolve
the existing struct to the AmigaOS layout adding the kernel-private
fields (`saved_regs`, `kstack`, `user_pt`, `sched_node`) behind
`tc_UserData` or in an appended internal block. Recommend the second
path — it lets the same Task object serve both kernel scheduler use
and `exec.library`'s view, which is how V36+ Exec was actually built.

## H6 — `struct Message` not yet defined; `struct RingSlot` is what flows

**Files:** `include/cara/msgport.h`, `include/cara/ring.h`

Phase 1 IPC carries `struct RingSlot` as the in-ring payload type
(`kind`, `length`, `payload`, `reserved`). V36+ requires every IPC
message body to begin with `struct Message { struct Node mn_Node;
struct MsgPort *mn_ReplyPort; UWORD mn_Length; }`. Programs use
`PutMsg(port, msg)` where `msg` is *any* struct prefixed with
`struct Message`. Today's RingSlot is incompatible.

**Resolution (post-sprint):** in Phase 3, `PutMsg` accepts a
`struct Message *`. The current `struct RingSlot` becomes a
kernel-private packing that wraps `struct Message *` (storing the
SASOS pointer + a kind tag). User code never sees RingSlot.

## M1 — Kernel-internal allocator is not `AllocMem` yet

**File:** `include/cara/alloc.h`

`Croi_Alloc` / `Croi_Free` are correct as brand-namespace internal
names. Phase 3 must also expose `AllocMem(size, requirements)` /
`FreeMem(ptr, size)` from `exec.library` with `MEMF_PUBLIC` /
`MEMF_CHIP` / `MEMF_FAST` / `MEMF_CLEAR` / `MEMF_ANY` /
`MEMF_REVERSE` / `MEMF_LOCAL` / `MEMF_24BITDMA` / `MEMF_KICK` flag
constants from `<exec/memory.h>`. The flag values must match V36+
verbatim. No drift today, but the public header needs to land before
the trampoline can compile.

**Resolution (post-sprint):** add `include/exec/memory.h` with
canonical flag values; route `AllocMem` LVO into `Croi_Alloc` (with a
flag-translation layer for MEMF_CHIP — irrelevant on RV2 — and
MEMF_PUBLIC — the SASOS default).

## M2 — Signal API needs its public LVO names

**File:** `include/cara/sched.h:124-138`

`Croi_AllocSignal` / `Croi_FreeSignal` / `Croi_Signal` / `Croi_Wait`
are correct internal names. Phase 3 needs `AllocSignal` (LVO -330) /
`FreeSignal` (-336) / `Signal` (-324) / `Wait` (-318) /
`SetSignal` (-306) trampolines that resolve to these.

**Resolution (post-sprint):** add `include/exec/tasks.h` with the
canonical prototypes; trampoline tables in `src/croi/exec_lib/`
populate the slots.

---

## M3 — AmigaOS integer types not yet defined

**File:** `include/cara/types.h`

Kernel uses `u8`/`u16`/`u32`/`u64`/`i32`/`usize`. Programs targeting
V36+ `<exec/types.h>` expect `UBYTE`/`UWORD`/`ULONG`/`BYTE`/`WORD`/
`LONG`/`APTR`/`BPTR`/`STRPTR`/`CPTR`/`RPTR` and the `BOOL`/`TRUE`/
`FALSE` macros. None exist today.

**Resolution (post-sprint):** add `include/exec/types.h` with the
canonical typedefs (`UBYTE = uint8_t` etc.) and the macro set. The
`BPTR`/`APTR` names are weighted — `BPTR` is the BCPL-flavoured
"shifted-by-2 longword pointer" used by `dos.library`; CaraOS will
define it as a regular pointer-sized opaque type because we are not
running BCPL, but the *name* is canonical.

## M4 — `struct Library` not yet defined

**Files:** none (gap, not drift)

V36+ `<exec/libraries.h>` defines `struct Library` (`lib_Node`,
`lib_Flags`, `lib_pad`, `lib_NegSize`, `lib_PosSize`, `lib_Version`,
`lib_Revision`, `lib_IdString`, `lib_Sum`, `lib_OpenCnt`) and the
flag constants `LIBF_SUMMING` / `LIBF_CHANGED` / `LIBF_SUMUSED` /
`LIBF_DELEXP`. CaraOS has the `KOBJ_LIBRARY` Kobj type but no
public-shape `struct Library` yet. `OpenLibrary` cannot return
anything spec-shaped until this lands.

**Resolution (post-sprint):** add `include/exec/libraries.h`, define
the canonical struct, and ensure each CaraOS library starts with a
`struct Library` prefix at the library base (negative-LVO range above
the prefix as classic Exec lays out).

## L1 — `dath.h` preamble misnames the public surface

**File:** `include/cara/dath.h:3-11`

Comment says "dath.library core". The public AmigaOS surface this
backs is `graphics.library`; "dath" is the brand-namespace
*implementation* name, not the library a program calls. Misleading
for new readers.

**Resolution (post-sprint):** update the comment to "`graphics.library`
core (brand-named **Dath** internally)" and drop the
"AmigaOS graphics.library analogue" line which understates the
relationship — it *is* the implementation.

**File:** `include/cara/test.h`

No drift. Test harness has no AmigaOS analogue and is correctly in
the brand namespace.

## L3 — `sched.h` mentions `Croi_Yield`, `Croi_TaskExit`, `Croi_TaskSetSelfPriority`

**File:** `include/cara/sched.h:96-105`

Brand-namespace internal kernel APIs. AmigaOS analogues that may want

## What is NOT drift

The audit considered and rejected the following as drift:

- `Croi_TrapDispatch`, `Croi_Time_Now`, `Croi_NewKernelPT`,
  `Croi_Page_Alloc`, `Croi_Print`, `Croi_Log`, `Croi_Halt`,
  `Croi_LoadElf`, `Croi_Syscall_Dispatch` — kernel-internal, no
  AmigaOS analogue. Brand namespace is correct.
- `Dath_Pixel`, `Dath_FillRect`, `Dath_DrawString`, `DathFramebuffer`,
  `DathConsole` — Phase 1 CPU rasteriser, kernel-internal. Brand
  namespace is correct. Phase 3 will add public `<graphics/*.h>`
  headers (`Move`, `Draw`, `RectFill`, `RastPort`, `BitMap`) that
  trampoline into these.
- `Ring_Enqueue`, `Ring_Dequeue`, `RingHeader`, `RingSlot` —
  kernel-internal IPC primitive, no AmigaOS analogue.
- `Fdt_*`, `struct Fdt`, `struct CroiPlatform` — pre-AmigaOS
  technology, kernel-internal. Brand namespace is correct.
- `KobjType`, `struct Kobj`, `struct HandleTable`, `Handle` — the
  internal handle / object substrate. AmigaOS programs see canonical
  pointers (`struct Library *`, `struct MsgPort *`); Handles never
  cross the API boundary.

land alongside the first user program that needs them in Phase 3.
