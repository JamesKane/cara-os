# Porting V36+ source to CaraOS

> How to build an AmigaOS Release 2 (V36+) application against CaraOS and
> run it as a Gleas. Phase 3's success criterion (`docs/ROADMAP.md`,
> `docs/PHASE3.md`) is that this needs **no source edits** — the API
> namespace is verbatim AmigaOS (PRINCIPLES §3.1), so a well-written
> Release-2 listing compiles and links against CaraOS headers unchanged.
> "Porting" is rebuild-and-link, not rewrite.
>
> This doc grows with Phase 3. Today it covers the P0 baseline: a program
> that opens `intuition.library` and a window. The worked example is
> `src/userland/v36hello.c`.

---

## 1. The promise, and the one rule

A CaraOS program reaches the OS through the **API namespace** —
`<exec/*>`, `<dos/*>`, `<intuition/*>`, `<graphics/*>`, `<proto/*>`,
`<utility/*>`, … — which carries the exact V36+ names, struct shapes,
and LVO numbers. Your source calls `OpenLibrary`, `AllocMem`,
`OpenWindow`, walks `struct Window`, uses IDCMP — all spelled the Amiga
way.

**The rule:** application source includes *only* the API namespace.
Never include `cara/*` (the kernel-internal brand namespace) and never
hand-roll a syscall — that is what makes the source portable. If you
find yourself reaching for `cara/sysno.h`, you are writing kernel code,
not an application.

`v36hello.c` holds to this: its only includes are `<exec/*>`,
`<intuition/*>`, `<proto/*>`.

---

## 2. How a call reaches the OS (so you can trust it)

Each library function is a `static inline` stub in `<proto/<lib>.h>`
(generated by `tools/lvo-gen` from `<lib>.conf`, `docs/LVO.md`). The
stub indexes the library's vec table at the negative side of its base
pointer and either calls in-process (`local`), `ecall`s into Croi
(`syscall`), or `PutMsg`s a server Gleas (`server`). Your code never
sees any of that — it just calls `OpenWindow(&nw)`.

Two base pointers follow the Amiga idiom:

- `SysBase` (exec.library) is bootstrapped by the C runtime before
  `main()`; you do not open it.
- Every other base is yours to open and assign: `IntuitionBase =
  (struct IntuitionBase *)OpenLibrary("intuition.library", 36);`. The
  `<proto/<lib>.h>` stubs index off that global, exactly as on AmigaOS.

---

## 3. The build recipe

A Gleas is a freestanding static ELF linked at user VAs, built with the
RV64 cross toolchain (Homebrew LLVM, `cmake/toolchain-riscv64.cmake`).
The pattern (see any target in `src/userland/CMakeLists.txt`):

- **Compile** with `cara_kernel_flags` (freestanding, `-std=c23`) and
  the `cara_headers` include path — which is where the API-namespace
  headers and the generated `<proto/*>` live. (`cara_headers` also
  exposes `cara/*`, but your source must not include those.)
- **Link** `-nostdlib`, the user linker script `src/userland/user.lds`,
  and the C runtime `libcara_user` (whole-archived so `_start` survives
  GC). `libcara`'s `_start` opens exec.library to set `SysBase`, calls
  `main()`, and turns the return value into the exit status (the role of
  the Amiga startup + amiga.lib — not your source).
- **Depend** on the generated stubs for the libraries you use
  (`cara_exec_lib_gen`, `cara_intuition_lib_gen`, …) so `<proto/*>` is
  generated before you compile.

`main()` returns an `int` exit code; `RETURN_OK` (0) / `RETURN_FAIL`
(20) are the AmigaDOS conventions (from `<dos/dos.h>` once dos.library
lands; P0 spells the literals).

---

## 4. Running it

Until Splanc + a real Workbench launch exist, a Gleas is embedded in the
kernel image and spawned — either by the live boot path (`entry.c`, when
a framebuffer is up) or by an in-kernel smoke test
(`Croi_SpawnUserTaskFromElf`). `v36hello` is spawned by
`KERNEL_TEST(v36hello_smoke)`, which stands up a screen, runs the ELF,
and asserts it returned `RETURN_OK` — the automated form of "it ran".

`OpenWindow(Screen = nullptr)` targets the active Workbench screen, so
something must have opened one (the boot desktop, or the test). That is
the normal Amiga situation: an application opens onto an existing screen.

---

## 5. What works today (Phase 3 progress)

P0 baseline: `exec.library` (a core slice — OpenLibrary, AllocMem,
ports, signals) and `intuition.library` (OpenWindow/CloseWindow,
gadgets) are live; a verbatim-V36 open-a-window program builds and runs.

The rest of the V36 surface arrives library by library (`docs/PHASE3.md`
epic order: exec → utility → dos → graphics → intuition → devices →
BOOPSI → gadtools → asl → …). Each library is **link-complete first**
(every documented LVO is declared at its canonical number, so your
program always links) with **bodies filled in apps-driven** — an
unimplemented function is a defined, logged stub, not a missing symbol.
If a call returns a not-yet-implemented failure, that gap is tracked,
not a porting error on your side.

Cross-building from a host is the path for now; the on-target compiler
(`tion`, Phase 6) is the eventual self-host story.
